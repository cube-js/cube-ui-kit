# Dialog

Dialogs are windows containing contextual information, tasks, or workflows that appear over the user interface. Depending on the kind of Dialog, further interactions may be blocked until the Dialog is acknowledged.

## When to Use

- Display important information or actions that require user attention
- Confirm or cancel user actions before proceeding
- Collect user input in a focused, contextual interface
- Show complex workflows or forms that need dedicated space
- Present alerts or notifications that require user acknowledgment

### Properties

- **`children`** — Dialog content (Header, Content, Footer, etc.)
- **`size`** `'small' | 'medium' | 'large' | 'S' | 'M' | 'L'` (default: `M`) — Dialog size (`S`/`M`/`L` are aliases for `small`/`medium`/`large`)
- **`styles`** — Custom styles for the dialog root
- **`closeButtonStyles`** — Custom styles for the close button
- **`isDismissable`** `boolean` (default: `false`) — Whether the dialog is dismissable (shows close button, allows Escape key)
- **`onDismiss`** `function` — Callback fired when the dialog is dismissed
- **`closeIcon`** — Custom close icon element
- **`role`** `'dialog' | 'alertdialog'` (default: `dialog`) — ARIA role for the dialog

Supports [Base properties](/docs/getting-started-base-properties--docs)

### Styling Properties

#### styles

Customizes the root element of the dialog.

**Sub-elements:**

- `Dialog` - The main dialog container
- `Content` - The content area wrapper
- `Header` - The header section wrapper
- `Footer` - The footer section wrapper

#### closeButtonStyles

Customizes the close button appearance.

### Style Properties

These properties allow direct style application without using the `styles` prop:

- **Base:** `display`, `font`, `preset`, `hide`, `whiteSpace`, `opacity`, `transition`
- **Dimension:** `width`, `height`, `blockSize`, `inlineSize`, `flexBasis`, `flexGrow`, `flexShrink`, `flex`
- **Block:** `border`, `blockBorder`, `inlineBorder`, `radius`, `shadow`, `outline`, `padding`, `blockPadding`, `inlinePadding`, `overflow`, `scrollbar`, `textAlign`
- **Flow:** `flow`, `place`, `placeItems`, `placeContent`, `alignItems`, `alignContent`, `justifyItems`, `justifyContent`, `align`, `justify`, `gap`, `columnGap`, `rowGap`, `gridColumns`, `gridRows`, `gridTemplate`, `gridAreas`

### Padding Tokens

`Dialog` declares its own gutters as custom properties on the dialog root, so every slot inside it — `Header`, `Content`, `Footer` — resolves the same values. They are part of the public contract and safe to read from a consumer's own styles:

| Token | Default | `type="popover"` | What it measures |
| --- | --- | --- | --- |
| `$dialog-padding-h` | `1.5x` | `1x` | Horizontal gutter on every slot |
| `$dialog-content-padding-v` | `1.5x` | `1x` | `Content`'s vertical padding |
| `$dialog-title-padding-v` | `1.5x` | `1x` | `Header`'s vertical padding |
| `$dialog-footer-v` | `1.5x` | `1x` | `Footer`'s vertical padding |

The case this exists for is a child that should span the full dialog width — an edge-to-edge table or divider — while its siblings keep the gutter. Take `Content`'s horizontal padding back and hand the same value to the siblings:

```jsx
<Dialog>
  <Content styles={{ padding: '$dialog-content-padding-v 0' }}>
    <Paragraph styles={{ padding: '0 $dialog-padding-h' }}>
      Keeps the dialog's gutter.
    </Paragraph>
    <FullWidthTable />
  </Content>
</Dialog>
```

A `styles` override on a slot is merged into the slot's own styles rather than replacing them, so `Content` keeps its `flexGrow`, `overflow` and height rules while only the padding changes. In plain CSS the same values are readable as `var(--dialog-padding-h)` and `var(--dialog-content-padding-v)`.

### Modifiers

The `mods` property accepts the following modifiers you can override:

- **`dismissable`** `boolean` — Applied when the dialog can be dismissed with close button or Escape key

`Footer` inside a dialog carries one modifier of its own:

- **`content-overflow`** `boolean` — Applied while the dialog's `Content` is taller than the room it has, i.e. while it scrolls. The footer draws its top border only then, so the line separates the actions from a body that continues beneath them and is absent under a body that fits.

The body is the `Content` that is a direct child of the dialog or of a direct-child `<form>`. A `border` in the footer's own styles replaces the default, so a footer can keep the line always or never draw it:

```jsx
<Footer styles={{ border: 'top' }}>{/* line always */}</Footer>
<Footer styles={{ border: false }}>{/* line never */}</Footer>
```

## Variants

### Types

- `dialog` - Standard dialog for general content (default)
- `alertdialog` - Alert dialog for critical notifications or confirmations

### Sizes

- `small` / `S` - Compact dialog for simple content (360px width)
- `medium` / `M` - Standard dialog for moderate content (479px width)
- `large` / `L` - Large dialog for complex content (798px width)

## Examples

### Basic Dialog

```jsx
<Dialog>
  <Header>
    <Title>Dialog Title</Title>
  </Header>
  <Content>
    <Paragraph>Dialog content goes here.</Paragraph>
  </Content>
  <Footer>
    <Button onPress={close}>Close</Button>
  </Footer>
</Dialog>
```

### Dismissable Dialog

```jsx
<Dialog isDismissable onDismiss={close}>
  <Header>
    <Title>Dismissable Dialog</Title>
  </Header>
  <Content>
    <Paragraph>You can close this dialog with the close button or Escape key.</Paragraph>
  </Content>
</Dialog>
```

### Custom Size Dialog

```jsx
<Dialog size="large">
  <Header>
    <Title>Large Dialog</Title>
  </Header>
  <Content>
    <Paragraph>This dialog uses the large size variant.</Paragraph>
  </Content>
</Dialog>
```

### Alert Dialog

```jsx
<Dialog role="alertdialog">
  <Header>
    <Title>Confirm Action</Title>
  </Header>
  <Content>
    <Paragraph>Are you sure you want to delete this item? This action cannot be undone.</Paragraph>
  </Content>
  <Footer>
    <Button type="danger" onPress={confirmDelete}>Delete</Button>
    <Button onPress={close}>Cancel</Button>
  </Footer>
</Dialog>
```

## Accessibility

### Keyboard Navigation

- `Tab` - Moves focus between interactive elements within the dialog
- `Shift + Tab` - Moves focus backward between interactive elements
- `Escape` - Dismisses the dialog if `isDismissable` is true
- `Enter/Space` - Activates focused buttons or interactive elements

### Screen Reader Support

- Dialog announces as "dialog" or "alertdialog" based on role
- Focus is trapped within the dialog when open
- Focus returns to the trigger element when dialog closes
- Dialog title and content are properly announced
- State changes and actions are communicated to screen readers

### ARIA Properties

- `aria-labelledby` - Links dialog to its title element automatically
- `aria-describedby` - Links dialog to its description content
- `aria-modal` - Set to true for modal dialogs to indicate exclusive interaction
- `role` - Set to "dialog" or "alertdialog" based on content type

## Best Practices

1. **Do**: Provide clear titles and actionable buttons

   ```jsx
   <Dialog>
     <Header>
       <Title>Save Changes</Title>
     </Header>
     <Content>
       <Paragraph>Your changes will be saved to the document.</Paragraph>
     </Content>
     <Footer>
       <Button type="primary" onPress={save}>Save</Button>
       <Button onPress={close}>Cancel</Button>
     </Footer>
   </Dialog>
   ```

2. **Don't**: Use dialogs for trivial notifications

   ```jsx
   {/* Avoid using dialogs for simple success messages */}
   <Dialog>
     <Content>Item saved!</Content>
   </Dialog>
   ```

3. **Wrapping the slots in a form**: A `Form` may sit directly between `Dialog` and its slots, so the submit button is inside it. A `Form` placed there lays itself out as the dialog's slot column, so `Content` still scrolls and `Footer` still pins with no styles of your own:

   ```jsx
   <Dialog>
     <Header><Title>Edit</Title></Header>
     <Form>
       <Content>{/* long body, scrolls */}</Content>
       <Footer>
         <Button type="primary" htmlType="submit">Save</Button>
       </Footer>
     </Form>
   </Dialog>
   ```

   Only a **direct child** `Form` is treated this way. A form nested deeper, or a plain `<form>` element, is your own layout and is left alone. The layout is the form's own state rather than a rule in `Dialog`, so `styles` on the form still win: `<Form styles={{ gap: '1x' }}>` puts `1x` between the slots.

4. **Accessibility**: Always provide a meaningful title for screen readers
5. **Dismissal**: Use `isDismissable` for dialogs that users can close voluntarily
6. **Focus Management**: Ensure focus moves to the most important action when dialog opens

## Integration with Overlays

Dialog is typically used within `DialogTrigger` or `Modal` components for proper overlay management and positioning. It should not be rendered directly without an overlay container.
