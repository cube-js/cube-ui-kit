# AlertDialog

A modal dialog for important messages that require user acknowledgment. Extends `Dialog` with predefined confirm/cancel actions. Not dismissable by default.

## When to Use

- Confirmation dialogs
- Error or warning messages
- Destructive action confirmations

## Properties

- **`title`** `string` — Dialog title
- **`content`** `ReactNode` — Dialog body content
- **`danger`** `boolean` — Applies danger styling for destructive actions
- **`noActions`** `boolean` — Hide the action buttons entirely
- **`actions`** `object` — Customize buttons:
  - `confirm` — Confirm button props or `false` to hide (default: `{ children: 'Ok', type: 'primary' }`)
  - `cancel` — Cancel button props or `true` to show (default: hidden, uses `{ children: 'Cancel' }`). Set a button's text with `children`; `label` still works but is deprecated
  - `secondary` — Optional secondary button props
- **`size`** `'S' | 'M' | 'L' | 'small' | 'medium' | 'large'` — The size of the dialog
- **`isDismissable`** `boolean` (default: `false`) — Whether the dialog is dismissable
- **`closeIcon`** `ReactElement` — Custom close icon element
- **`closeButtonStyles`** `Styles` — Custom styles for the close button

### Base Properties

Extends [Dialog](/docs/overlays-dialog--docs) and supports [Base properties](/docs/getting-started-base-properties--docs).

### Style Properties

These properties allow direct style application without using the `styles` prop:

- **Base:** `display`, `font`, `preset`, `hide`, `whiteSpace`, `opacity`, `transition`
- **Position:** `gridArea`, `order`, `gridColumn`, `gridRow`, `placeSelf`, `alignSelf`, `justifySelf`, `zIndex`, `margin`, `blockMargin`, `inlineMargin`, `inset`, `blockInset`, `inlineInset`, `position`, `scrollMargin`, `blockScrollMargin`, `inlineScrollMargin`, `scrollPadding`, `blockScrollPadding`, `inlineScrollPadding`
- **Dimension:** `width`, `height`, `blockSize`, `inlineSize`, `flexBasis`, `flexGrow`, `flexShrink`, `flex`
- **Block:** `border`, `blockBorder`, `inlineBorder`, `radius`, `shadow`, `outline`, `padding`, `blockPadding`, `inlinePadding`, `overflow`, `scrollbar`, `textAlign`
- **Color:** `color`, `fill`, `fade`, `image`
- **Text:** `textTransform`, `fontWeight`, `fontStyle`
- **Flow:** `flow`, `place`, `placeItems`, `placeContent`, `alignItems`, `alignContent`, `justifyItems`, `justifyContent`, `align`, `justify`, `gap`, `columnGap`, `rowGap`, `gridColumns`, `gridRows`, `gridTemplate`, `gridAreas`

## Examples

### Confirmation dialog

```jsx
<DialogTrigger>
  <Button>Delete Item</Button>
  <AlertDialog
    title="Confirm Delete"
    content="Are you sure you want to delete this item?"
    actions={{
      confirm: { children: 'Delete', type: 'danger' },
      cancel: true,
    }}
  />
</DialogTrigger>
```

### Info dialog (confirm only)

```jsx
<AlertDialog
  title="Update Available"
  content="A new version is available. Please refresh to update."
/>
```

## Imperative API

`useAlertDialogAPI()` opens an alert dialog from code, such as an event handler, with no `DialogTrigger` to render. It works anywhere under `<Root>`.

- **`open(props, params?)`** `Promise<'confirm' | 'secondary'>` — Opens the dialog. Resolves with the action the user picked, and rejects when the dialog closes without one or cannot open.

`props` takes the properties above, plus:

- **`onConfirm`** `() => unknown` — Runs when the confirm button is pressed. If it returns a promise, the dialog stays open until it settles (see below)
- **`onSecondary`** `() => unknown` — The same, for the secondary button
- **`onCancel`** `() => void` — Runs when the dialog settles as a cancel: the Cancel button, Escape, a click outside, an aborted `cancelToken`, or `content` calling `reject()`
- **`type`** — The dialog container type, as on `DialogContainer`
- **`isDismissable`** `boolean` (default: `true`) — Whether Escape and a click outside close the dialog
- **`onDismiss`** `(action?: string) => void` — Called when an action button, Escape or a click outside closes the dialog. An action button passes its name: `'confirm'`, `'secondary'` or `'cancel'`
- **`content`** can also be a function `({ resolve, reject }) => ReactNode`, for content that closes the dialog itself

`params` takes:

- **`cancelToken`** `AbortSignal` — Closes the dialog when aborted

The confirm button resolves `'confirm'` whether you configure `actions.confirm` or leave the default Ok button. Set it to `false` to hide it.

### Running the action

Pass the action as `onConfirm` and ignore the returned promise. A cancel then needs no handling: an ignored cancel is not reported as an unhandled rejection.

```jsx
const { open } = useAlertDialogAPI();

const onDelete = () => {
  open({
    title: 'Delete the item?',
    content: 'This cannot be undone.',
    danger: true,
    actions: { confirm: { children: 'Delete' }, cancel: true },
    onConfirm: () => deleteItem(),
  });
};

<Button onPress={onDelete}>Delete</Button>;
```

When `onConfirm` or `onSecondary` returns a promise, the dialog waits for it:

- The pressed button shows a loading state, the other buttons are disabled, and Escape and a click outside are ignored.
- When the promise resolves, the dialog closes and `open` resolves with the button's status.
- When it rejects, or the handler throws, the dialog stays open with its buttons enabled again, so the user can retry or cancel. The error is passed to `reportError`, which reaches error reporting such as Sentry. To show it to the user, catch it inside the handler, for example with a toast.

`actions.confirm.onPress` and `actions.secondary.onPress` behave the same way, but they are deprecated: put the action in `onConfirm` or `onSecondary`. If both are set, both run and the dialog waits for both.

A choice between two actions needs no promise either:

```jsx
open({
  title: 'Unsaved changes',
  actions: {
    confirm: { children: 'Save' },
    secondary: { children: 'Discard' },
    cancel: true,
  },
  onConfirm: async () => {
    await save();
    navigate('/');
  },
  onSecondary: () => navigate('/'),
});
```

### How the promise settles

| Event | Promise |
| --- | --- |
| Confirm or secondary action | resolves `'confirm'` / `'secondary'`, once its handler has finished |
| Cancel action | rejects with `undefined` |
| Escape or a click outside | rejects with `undefined` |
| `cancelToken` aborted, before or while the dialog is open | rejects with `undefined` |
| `content` calls `resolve(status)` | resolves `status` |
| `content` calls `reject(reason)` | rejects with `reason` (`undefined` for `reject()`) |
| Another alert dialog is open | rejects with an `Error` |

A rejection with `undefined` is a cancel: the user chose not to act. Anything else is a real failure. An ignored promise stays quiet on a cancel and still reports a real failure as an unhandled rejection. Once you `await` the promise or chain `.then`, the cancel reaches your code, so handle it there.

### Waiting for the result

Await the promise only when the caller itself needs the answer, such as a guard that returns whether the user agreed:

```jsx
const confirmLeave = async () => {
  try {
    return (await open({ title: 'Leave the page?', actions: { cancel: true } })) === 'confirm';
  } catch (reason) {
    // Cancel, Escape or a click outside
    if (reason === undefined) return false;

    // A real failure, such as another dialog being open
    throw reason;
  }
};
```

### Closing the dialog from code

```jsx
const { open } = useAlertDialogAPI();
const controllerRef = useRef(null);

const onRequestApproval = () => {
  // A signal stays aborted, so each dialog needs a fresh controller.
  controllerRef.current = new AbortController();

  open(
    {
      title: 'Waiting for approval',
      content: 'The dialog closes when the approval arrives.',
      actions: { confirm: { children: 'Hide' } },
    },
    { cancelToken: controllerRef.current.signal },
  );
};

// Later, for example when the approval arrives:
controllerRef.current?.abort();
```

Aborting settles the dialog as a cancel. A signal that is already aborted settles it right away, without showing the dialog.

### One dialog at a time

Only one alert dialog can be open: while one is, `open` rejects with an `Error`. A dialog that is already closing gives way to the new one, so a follow-up dialog opened from the previous one's result, such as a second confirmation, shows normally. The dialog is still open while its `onConfirm` runs, so open a follow-up after the handler, not from inside it.
