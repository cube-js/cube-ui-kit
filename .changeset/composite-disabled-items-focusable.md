Keyboard navigation now stops on a disabled item instead of skipping it, as `Menu` and `CommandMenu` already do and as WAI-ARIA recommends, so a keyboard or screen reader user hears it, its description and that it is disabled. This covers `ListBox` and the fields built on it (`Picker`, `Select`, `ComboBox`, `FilterListBox`, `FilterPicker` in list and tree mode, `SearchComboBox`, `CommandTextArea`, `TagInput`'s options), `Tree`, `Tabs`, `ToggleGroup` (with or without a tooltip), `TagInput`'s locked chips, and `ItemTable` rows. The item stays disabled: `aria-disabled`, never selected, toggled, removed, expanded, activated, dragged or reordered, and Enter, Space and a click do nothing. A disabled `ItemTable` row can no longer be dragged with the pointer either, and a disabled `Tree` row no longer opens its menu with a right-click, a long press or `Shift+F10`, as a disabled `ItemTable` row doesn't. A list that highlights an option on its own as you type still picks the first one you can choose, a `TagInput` search that matches only disabled options now lists them, and a `TagInput` option disabled with its own `isDisabled` is refused like one in `disabledKeys`. A fully disabled field or group stays out of the keyboard, and so does a disabled option in a `ListBox` where focus selects (`selectionBehavior="replace"`). Two bugs are fixed along the way: the `Tabs` overflow picker listed a disabled tab as an option you could choose, which activated it, and in an `ItemTable` with tree rows the arrow keys moved focus onto the table itself when the next row was disabled. Tests that expected the arrow keys to skip a disabled item need updating.
